# Подготовка ответа в чате

Решение: временная плашка на месте следующего сообщения помощника. В первой строке — три движущиеся точки и текущий этап, ниже — тематические метки сервера. Метки переносятся на следующую строку на узком экране. Проценты, предполагаемое время ожидания и искусственная смена этапов не используются.

| Этап API | Подпись |
| --- | --- |
| `queued` | Запрос принят |
| `analyzing` | Учитываю контекст диалога |
| `preparing_answer` | Готовлю ответ |
| `finalizing` | Сохраняю результат |

Если `progress` отсутствует или этап неизвестен, подпись — «Готовлю ответ». При пустом `keywords` меток нет. Плашка не сохраняется в истории. Скринридер получает обновления через `role=status`; системная настройка уменьшения движения применяется к анимации.

POST `/sessions/{id}/turns` и последовательные GET `/sessions/{id}/turns/{turn_id}` отправляются с `include_progress=true`. Каждый следующий опрос начинается после предыдущего с задержкой `poll_after_ms` (существующий защитный диапазон клиента: 50–5000 мс; по умолчанию 700 мс). Синхронный ответ показывается сразу. При завершении или ошибке плашка удаляется. Уход из диалога отменяет текущий запрос и дальнейший опрос; поздний ответ не применяется. Прерванное сообщение можно повторить с тем же UUID и текстом.

Источник протокола — предоставленная заметка HackChange Frontend Turn Progress, версия бэкенда `ba82cb6`. 16 ноября актуальный `origin/main` влит в ветку фронтенда: бэкенд сохраняет этап и метки в БД, а фронтенд использует `TurnProgress` из обновлённой сгенерированной схемы. `progress: null` и отсутствие поля дают подпись «Готовлю ответ». Новые этапы покрыты серверными и модульными клиентскими тестами; браузерная приёмка остаётся отдельной проверкой.

Реализация: `frontend/src/TurnIndicator.tsx`, `frontend/src/api/service.ts`, `frontend/src/App.tsx`.
